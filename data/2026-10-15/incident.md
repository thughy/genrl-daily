# 事故复盘：10-14 回扫只覆盖了半批（API 部分索引），1,161 篇未筛

- 级别：中（10-14 批次约 57% 的论文没被筛过，其中有本期必读 IsoVRBench；无外部影响）
- 发现方式：10-15 例行 run 自查发现（按 watchlist 去读 SyncReward 2610.16338 时，发现它不在 10-14 审计的 api.json 里）。这次是我自己发现的。
- 时间均为北京时间

## 1. 发生了什么
10-14 回扫在 10:20 拉 arXiv API（submittedDate 窗口），得到 878 篇，最新一篇 published = 10-12 06:09 UTC，最大编号 2610.16234。当时把 878 当成整批数量写进了事故复盘和网站。实际上那一批（10-09 18:00 UTC – 10-13 18:00 UTC 投稿，10-13 20:00 ET 公告）在我的 10 个分类里有 2,039 篇（编号到 2610.18874）。10-14 10:20 时 API 索引只建到一半。

## 2. 证据（三路独立）
- 10-15 重拉同一窗口 API：2,039 篇（10 类），其中 1,161 篇不在 10-14 的 api.json 里。
- 10-15 用带随机参数的 RSS（lastBuildDate 00:32 UTC、age=0，pubDate = Wed 14 Oct）：new + cross 共 2,153 条，API 的 2,039 篇全部在内。
- cs.CV pastweek 页头：「Wed, 14 Oct 2026 (479 entries)」，编号覆盖 2609.26315–2610.18874。

## 3. 根因
1. G1 把「API 计数」当作召回真值，但没有检查**完整性**：公告后的几个小时内 API 索引在逐步建立，计数会偏少。878 篇的最新 published（10-12 06:09 UTC）离批次截止（10-13 18:00 UTC）差了约 36 小时，这本身就是缺口信号，没有被检查。
2. G8 要求「API 计数与列表页日期」一起报，但没要求两个**数量**对得上；当时列表页是缓存旧页，没有可比的数量。
3. 10-15 早上又看到同类现象：08:00 公告后 API 到 08:55 仍为 0；不带版本号的 abs 链接返回缓存的 404，带 v1 的 abs 页却已能打开，并且新编号是逐步放出的（08:37 到 2610.19486，08:55 到约 2610.19800）。如果只看 API 或只看不带版本号的 abs，会再判一次「未公告」。

## 4. 修正（自动可检查，已写入 scope.md 事故护栏 G9，待 Henry 确认）
- G9a 完整性：API 窗口里最新 published 必须在批次截止前 1 小时以内，否则判「部分索引」，不得据此报数或下结论，30 分钟后重拉。
- G9b 数量对账：API 计数要与一个独立总数对账——带随机参数的 RSS（lastBuildDate 新、pubDate = 预期公告日）的 new+cross 条数，或 age<1h 的列表页页头条数；差距 >10% 判不完整（RSS 含旧编号的交叉列表，10-14 实测约多 5%：API 1,865 vs RSS 1,968，9 类）。
- G9c abs 探测一律带版本号（/abs/<id>v1）；不带版本号的 404 可能是缓存。
- G9d 公告后 2 小时内的结论都标「初步」，当天 run 结束前重拉一次 API 复核数量。
- 已写 tools/recall_check.py 做 G9a/G9b（输出：API 计数、最新 published、RSS 条数与 pubDate、是否通过）。
